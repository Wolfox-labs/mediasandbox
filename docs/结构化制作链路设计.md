# 结构化制作链路设计

> **状态**：设计稿，尚未实现。
> **目的**：把"做网页"从"调一次大模型"变成**决策模型逐块决策结构、生成层逐块填充、可验证、可干预、可沉淀**的链路。
> **前置阅读**：[系统说明.md](系统说明.md)（现状）、[架构与业务逻辑.md](../架构与业务逻辑.md)（与旧蓝图的偏差）

---

## 一、为什么需要这份设计

### 1.1 现状的病根不是"编排弱"，是"颗粒度太粗"

用当前系统"做一个网页"，实际发生的事：

```
决策模型选一个工具（5 选 1，必然选 scaffold-frontend）
  → 调一次大模型，吐出一个完整的 HTML 字符串
  → 写盘 → 校验文件非空 → 结束
```

**一次 LLM 调用产出一个静态文件。** 于是：

| 机制 | 实际状态 |
|---|---|
| 决策模型 | 只回答"选哪个工具"，5 选 1 且答案几乎注定 |
| DAG 编排 | 只有一个节点，退化成单点 |
| 兜底状态机 | 不失败就走不到 |
| 沙盒隔离 | 写个 HTML，没有不可信代码要隔离 |
| 双 provider 一致性 | 同上 |

**所有机械都在空转。** 根因是：**工具是"交付物级"粒度**（整页、整篇、整图），下面没有可编排的东西。

### 1.2 由此缺失的四层能力

| # | 缺失 | 本质 |
|---|---|---|
| 1 | **结构层** | 页面结构藏在 LLM 生成的字符串里，不可决策、不可干预 |
| 2 | **素材层** | 工具入参只有文本，素材无处安放（"图嵌不进页面"的真实原因） |
| 3 | **验证层** | 沙盒只跑一次性命令，不维持长驻进程，页面跑不起来也就无法验证交互 |
| 4 | **人在回路** | 一键提交→异步跑完的单向流程，只能看和硬取消，不能指导 |

### 1.3 目标链路

```
① 生成前    block 候选池（分组）→ 用户选取 → 本次候选集
                        可选：套用模板（限定范围 / 起手结构）
② 制作中    决策模型逐块决定结构（choice / noul / numeric / score）
                        逐块实现（生成层：文案 / 图 / 代码）
                        每块是独立产物，可替换、可干预
③ 验证      沙盒里真跑起来 → 决策模型模拟点击（廉价测试体）
                        不通过则回到某块重做
④ 沉淀      成品结构 → 存为新模板 → 下次起手就用（越用越好用）
```

**贯穿全程**：用户可暂停、可看详细流程、可随时指导。

## 二、核心设计决策

### 2.1 结构由决策模型决定，不由大模型决定

这是**整份设计的地基**，也是与"让大模型生成 block"方案的根本分野。

| 环节 | 谁决定 | 用什么原语 |
|---|---|---|
| 下一块放什么 | **决策模型** | `choice`（候选来自 block 池） |
| 还要不要再来一块 | **决策模型** | `noul` |
| 要几个（如 feature 条数） | **决策模型** | `numeric` |
| 这个结构好不好 | **决策模型** | `score` |

**生成层一次都没有决定过结构。** 它只被调用去实现已经定好的 block。

> **为什么这条重要**：如果让大模型"生成需要哪些 block"，那"选结构"就是生成层做的，
> 决策模型只能干看着 —— **沦为装饰**。这正是现状的病根，不能在结构化之后重演。
>
> 大模型**可以提议**一个新的 block 类型，但提议要进 block 池、**经过注册与校验**，
> 之后才能被选中。**提议 ≠ 决定。**

顺便：`numeric` 与 `score` 两个原语**已实现但从未被使用**。在 block 化之后，
"要几个"和"好不好"这两类问题才真正出现 —— 它们终于有了落点。

### 2.2 block 池是候选集的来源（与工具注册表同构）

现有架构的核心原则是「**候选集来自工具注册表**，所以扩展工具链 = 改注册表，不需重训模型」。

block 池沿用同一条原则：**决策模型只在本次候选集里选**，而候选集来自 block 池。

```
block 池（按分组组织）
   ├─ 内置 block          ← 我们提供的词表
   ├─ 模型提议的          ← 生成层提议 → 注册校验 → 入池
   ├─ 用户手打的          ← 人工定义
   └─ 导入的              ← 外部来源
        ↓ 用户从池里选取本次要用的
   本次候选集
        ↓
   决策模型在此范围内逐块选择
```

**后三类是用户可选项，不是必选项。** 用户不参与时，用内置集合即可跑通全流程。

### 2.3 复用 `frontend` 还是新增环境

**新增 `webpage`，与现有 `frontend` 并存。**

理由：现有 `frontend` 链路（整页生成）是通的、有测试覆盖、有真实产出验证过。
结构化制作是一条**新链路**，直接改造会同时破坏两条路。

| envType | 含义 | 工具粒度 |
|---|---|---|
| `frontend` | 整页生成（现状，保留） | 交付物级 |
| **`webpage`** | **结构化制作（新增）** | **block 级** |

## 三、结构化中间表示

### 3.1 页面 = block 序列

页面不再是字符串，而是**数据**：

```json
{
  "templateId": "product-launch",
  "blocks": [
    { "id": "b1", "type": "hero",
      "slots": { "title": "…", "subtitle": "…", "media": "artifacts/b1-hero.png" },
      "status": "filled" },
    { "id": "b2", "type": "features",
      "slots": { "items": ["…", "…", "…"] },
      "status": "filled" },
    { "id": "b3", "type": "cta",
      "slots": { "text": "立即体验", "href": "#" },
      "status": "pending" }
  ]
}
```

**关键性质**：

| 性质 | 为什么重要 |
|---|---|
| 每个 block 有稳定 `id` | 可单独替换、重做、干预 |
| 每个 block 有 `type` | 结构可枚举，用户能说"把这块换成图集" |
| 每个 block 有 `slots` | 素材的落点。slot 是**有名字、有类型**的，下游接得上 |
| 每个 block 有 `status` | 支持"部分完成"与断点续做 |

### 3.2 block 类型词表（15 类，分 3 组）

| 分组 | block |
|---|---|
| **页面骨架** | `hero` / `features` / `gallery` / `cta` / `footer` / `nav` |
| **内容块** | `text` / `image` / `video` / `code` / `quote` / `table` |
| **交互块** | `form` / `tabs` / `accordion` |

**15 < 26**，低于 `MAX_OPTIONS_PER_QUESTION` 上限，**单问即可，不需要分层**。
但分组仍有价值：界面上按组展示、提问时可指定"只在骨架组里选"。

**三类分组各有用途**：
- 骨架组决定页面**版式**
- 内容组决定**信息形态**
- 交互组是 ③ 验证环节的**测试对象**（有交互才有点击可模拟）

### 3.3 slot 类型

每个 block 声明自己的 slot 与类型。类型决定**由谁来填**：

| slot 类型 | 谁来填 | 例 |
|---|---|---|
| `text` | 生成层（LLM 写） | hero 的标题、段落 |
| `image` | 生成层（生图 API） | hero 的主视觉、图集 |
| `code` | 生成层（LLM 写） | code 块的代码 |
| `list<text>` | 生成层（LLM 批量写） | features 的条目 |
| `link` | 确定性 | cta 的 href |
| `literal` | 用户指定 | 页脚版权 |

**这张表是"素材填充"的落点**：每个 slot 独立决定"用什么、怎么实现"，
而不是让 LLM 一揽子吐出来。

## 四、逐块决策的提问设计

### 4.1 五类问题

| 问题 | 原语 | 候选 | 何时问 |
|---|---|---|---|
| `next_block` | `choice` | 本次候选集（按组） | 每轮 |
| `continue_structuring` | `noul` | — | 每轮（除首块） |
| `slot_count` | `numeric` | — | 该 block 有 `list` 型 slot 时 |
| `structure_quality` | `score` | — | 结构定稿后 |
| `slot_source` | `choice` | 生成式 / 确定性 | 每个 slot |

### 4.2 批量提交是必须的，不是优化

rizzo-flow **单模型常驻，并发请求会串行化**。逐块决策意味着一轮多次提问，
一次一问会把延迟累加得不可接受。

现有架构本来就以**批量为主要接口**（官方数据：21 问批量 1.0s vs 逐问 8.1s）。
结构化制作要把这一点用足 —— **一轮的所有问题打包成一次请求，共享同一次 prefill**。

```
第 1 轮：[next_block, slot_count, continue_structuring]        ← 一次请求
第 2 轮：[next_block, slot_count, continue_structuring]        ← 一次请求
…
定稿后：[structure_quality]                                     ← 一次请求
```

**代价提醒**：block 越多，决策轮次越多，决策层调用次数线性增长。
但单次约 50ms（热缓存 0.5s），且共享 prefill，几十轮是可接受的 ——
**这正是"决策模型当廉价判断器"的正确用法**，比每块调一次大模型便宜几个数量级。

### 4.3 阈值不要设在 0.5 附近

官方警告：共享前缀打分会移动接近的判定（Q8_0 时 777 中 13 个；Q4 时 63 中 2 个）。
所以 `noul` / `score` 的判定阈值应避开 0.5，建议 0.6/0.4 双阈值带滞回。

## 五、沙盒与验证（第 ③ 层）

### 5.1 现状缺口

沙盒现在只跑**一次性命令**（`exec` 一条命令拿退出码），**不维持长驻进程**。
所以跑不了 dev server，页面打不开，也就无法验证交互。

### 5.2 需要补的能力

| 能力 | 说明 |
|---|---|
| **长驻进程** | 起 dev server 并保持，与一次性 exec 并存 |
| **端口映射** | 容器内端口要能被宿主访问（供模拟点击） |
| **浏览器驱动** | 无头浏览器进沙盒或宿主侧驱动 |
| **截图 / DOM 快照** | 作为判定输入与产物 |

> Docker provider 现在默认 `network=none`（没有网卡）。验证场景需要在
> **受限但可用**的网络策略下运行 —— 这是安全与功能的取舍点，要单独设计。

### 5.3 决策模型当廉价交互测试体

这是本项目**独有**的用法：

| 做什么 | 怎么做 |
|---|---|
| 模拟用户点击 | 给定 DOM 快照 + 候选可点元素 → `choice` 选一个 |
| 判定交互是否成立 | 点击后状态变化 → `noul`（是否符合预期） |
| 判定可用性 | 页面结构 + 文案 → `score` |

**为什么用决策模型而不是大模型**：单次前向约 50ms、**0 生成 token**、
本地无网络、可跑几十上百次。用它做**大规模廉价试探**，把贵的判断留给大模型。

> 这条能力我们**有材料却一直没用**：`choice`/`noul`/`score` 三个原语都现成，
> 只是从没被用于"模拟用户"。

### 5.4 失败的处置

验证不通过时，**回到具体某个 block 重做**，而不是整条重来。
这正是 3.1 里"每个 block 有稳定 id 与 status"的用处 —— 可定点修复。

```
验证不通过
   ↓ 决策模型定位到问题 block
   ↓ 该 block 标记 pending，其余保留
   ↓ 重新填充该 block → 重新验证
```

## 六、人在回路（第 ④ 层）

### 6.1 现状

| 能力 | 有没有 |
|---|---|
| 看详细流程 | ✅ 有（决策过程 + 分层步骤 + WebSocket 实时推送） |
| 随时停止 | ⚠️ 有 `cancel`，但是**硬中止**，不能停在某点继续 |
| **随时指导** | ❌ **完全没有** |

### 6.2 需要的干预点

| 时机 | 用户能做什么 |
|---|---|
| 生成前 | 从 block 池**选取**本次候选集；选模板；手打/导入 block |
| 结构中 | 暂停；改"下一块"的选择；增删改某个 block；调整顺序 |
| 填充中 | 指定某个 slot 用生成式还是确定性；替换素材 |
| 验证后 | 看判定与截图；指定哪个 block 重做 |
| 结束后 | 把成品结构**存为新模板** |

### 6.3 实现机制

需要一个**暂停 - 指导 - 恢复**的通道，而不是只有 cancel：

```
运行中 ──暂停──→ 挂起（保留中间状态）
                    ↓ 用户指导（改结构 / 换素材 / 加约束）
                 恢复 ──→ 从挂起点继续
```

**关键约束**：挂起时必须**保留结构化中间表示**（页面数据），
这正是 3.1 存在的意义 —— 有数据才能暂停，字符串没法暂停。

## 七、模板与沉淀（"越用越好用"）

### 7.1 模板的两种用法

| 用法 | 含义 |
|---|---|
| **限定范围** | 选了模板，本次只在该模板的 block 集合内工作（防跑偏） |
| **起手结构** | 模板给出一个初始 block 序列，可在其上增删改 |

> 注意与现状的区别：现在 `static-page-from-template` 是**把结构硬编码在 TS 里**，
> 且**不可改**。新设计的模板是**数据**，可改、可派生、可沉淀。

### 7.2 从历史生成新模板

这是**护城河，不是功能**：

```
跑过的项目（结构 + 素材 + 验证结果都留痕）
   ↓ 提取可复用的结构
新模板
   ↓ 下次起手就用
越用越好用
```

因为结构是数据、决策有留痕、验证有结果 —— **这些数据天然构成训练与复用材料**。
一本字符串形态的 HTML 做不到这一点。

## 八、前端重做（Vue 3）

### 8.1 为什么要重做

现有前端是 **React 18 + Vite + Tailwind**（2374 行，四个标签页）。
结构化制作引入了**大量新交互**：

- block 池的分组浏览与多选
- 结构画布（拖拽排序、增删改 block）
- 每个 block 的 slot 编辑与素材替换
- 暂停/指导/恢复的流程控制
- 素材管理页（模板、block 组件、分组）

这些是**管理后台形态**的密集交互，与现有"看板"形态不同。
用一套成熟的后台框架（组件库、表格、表单、树、拖拽）会显著省力。

### 8.2 技术栈（按 vue-admin 规范）

| 项 | 选型 |
|---|---|
| 框架 | **Vue 3**（Composition API + `<script setup>`） |
| 语言 | TypeScript |
| 构建 | Vite |
| 状态 | Pinia（Setup Store，**扁平目录**，无 `modules/`） |
| 路由 | Vue Router |
| 样式 | **UnoCSS（无语义微调）+ SCSS（BEM 结构性样式）** |
| 目录 | `api/` `components/` `composables/` `layouts/` `router/` `stores/` `views/` |

**关键规范约束**（来自 vue-admin）：

- 类型**不用 `VO`/`DTO` 后缀**：`BlockItem` / `BlockForm` / `BlockQueryParams`
- 布尔值加 `is`/`has`/`can`/`should` 前缀
- `handle*` **仅用于流程编排**，单一动作用动词命名
- API 用 `const XXXAPI = {}` **对象字面量**，不用 class 静态方法
- BEM 带页面前缀：`block-pool__item--selected`
- **同一元素原子类 ≤ 3 个**，结构性样式（颜色/圆角/阴影）收敛到 SCSS
- 颜色用 CSS 变量，不硬编码
- SFC 块顺序：`template` → `script setup` → `style scoped`
- 组件 ≤ 300 行

### 8.3 迁移策略

**不做原地替换，先并存后切换**：

1. 新建 `packages/admin`（Vue 3），与现有 `packages/web` 并存
2. 后端 API 保持不变（REST 契约已稳定），新前端复用同一套接口
3. 结构化制作的新功能**只在新前端做**
4. 等新前端覆盖了现有四个标签页，再下线 `packages/web`

这样避免"重写期间旧界面不可用"，也避免两套代码长期并存。

> **代价要认清**：现有 2374 行 React 代码要重写。但其中「决策过程 / 分层步骤」
> 的逻辑（`state/run-view-model.ts`，233 行）与 React 无关，是**纯函数**，
> 可以近乎原样移植到 Vue（Pinia store 或 composable）。

## 九、素材管理页

新增一块独立页面，管理**可复用的制作素材**：

| 标签 | 内容 |
|---|---|
| **模板** | 内置模板 + 从历史沉淀的模板；查看/编辑其 block 序列 |
| **block 组件** | block 池的完整列表；按组浏览；查看 slot 定义 |
| **分组** | 分组的新增/重命名/排序 |
| **素材库** | 已产出的图片/文案，可被后续项目复用 |

**与生成前流程的关系**：这个页面就是"block 候选池"的管理界面 ——
用户在制作前从这里**选取**本次要用的 block。

## 十、分阶段落地

| 阶段 | 内容 | 依赖 | 可验证的产出 |
|---|---|---|---|
| **P1** | block 注册表 + 结构化中间表示 + 逐块决策（用上 `numeric`/`score`） | 无 | 跑出一个**结构是数据**的页面 |
| **P2** | 逐块填充（先做确定性实现，零成本跑通） | P1 | 每个 slot 有内容，页面可打开 |
| **P3** | Vue 3 前端骨架 + 结构画布 | P1 | 能看见并编辑结构 |
| **P4** | 素材管理页（模板 / block / 分组 / 素材库） | P3 | 用户能选池子 |
| **P5** | 沙盒长驻进程 + 浏览器驱动 | P2 | 页面跑起来、能截图 |
| **P6** | 决策模型模拟点击 + 定点重做 | P5 | 交互验证闭环 |
| **P7** | 暂停/指导/恢复 | P3 | 人在回路 |
| **P8** | 历史沉淀为模板 | P4 | 越用越好用 |

**P1 是地基**：结构一旦成为数据，后面所有阶段才有对象可操作。
**P2 必须先做确定性实现** —— 保证零成本可跑通，再考虑接生成层。

## 十一、明确不做的

| 项 | 为什么 |
|---|---|
| 让大模型决定结构 | 会让决策模型沦为装饰，重演现状病根 |
| 改造现有 `frontend` 链路 | 它是通的、有测试，改造会同时破坏两条路 |
| 原地替换 React 前端 | 重写期间旧界面会不可用。先并存 |
| 追求自由嵌套的 block 树 | 不可枚举 → 无法决策、无法干预、无法验证 |
