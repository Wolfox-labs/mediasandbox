## 一、成本纪律（最高优先级）

这一条排在最前面，因为它**多次被强调**，且违反了就是直接的经济损失。

### 1.1 用户原话

> 🗣 **「不要太多实测！跑的都是我的钱！实测生图要经过我的许可！！！」**

> 🗣 **「允许10次以内图像调用，主agent允许deepseek v4.1 flash」**

> 🗣 **「使用image 2即可」**

> 🗣 **「生图集成可以继续，调用生图时向我申请即可」**

### 1.2 由此推出的结论

| 资源 | 授权额度 | 是否需要逐次申请 |
|---|---|---|
| **生图调用** | 累计 ≤ 10 次，模型 `gpt-image-2` | ✅ **每次都要先问** |
| 文本模型调用 | 允许用 `spe/deepseek-v4.1-flash` | 仍需克制，非必要不调 |
| 本地推理（rizzo-flow） | **无限制** | ❌ 本地、0 生成 token、不花钱 |
| 确定性工具 | **无限制** | ❌ 不调任何模型 |

**工程含义**：默认实现必须**零成本可跑通**。生成式是**增强**，不是前提。

这不是"省钱技巧"，而是设计要求——它逼出了正确的架构：
确定性填充先跑通全链路，生成层接上来时只替换单个 slot 的实现，链路本身不动。

🔧 **执行中的教训**：本轮全程花费 **0 元**（未调文本模型、未调生图），
产出了 21KB 完整页面、375 个测试全绿、两个 provider 产物逐字节一致。
**零成本并不等于低质量验证**——本地真机 rizzo-flow 6 次调用 1.42 秒，
拿到的就是真实决策模型的行为。

### 1.3 容易被忽略的花钱点

- 文本端点（`api.wolfoxlabs.xyz`）**也是计费的**，不是只有生图花钱。
- "探活/探测"看似无害，反复探就是反复花钱。**探测要一次问清，不要试错循环。**
- 失败重试会放大成本。🔧 本轮踩过：一个无限重试循环跑满 300 秒，
  如果那次接的是付费端点，就是 700 次无效调用。

## 二、决策层的定位（架构地基，不可动摇）

### 2.1 用户原话

> 🗣 **「让大模型生成需要哪些block，然后再填充这些？可是这不就是大模型做的了，跟决策模型有什么关系？」**

这句话点出了整个项目的**根本风险**。用户随后确认了分工原则。

> ⚠️ **署名说明**：「结构由决策模型决定，不由大模型决定」这句话的**措辞是我总结的**，
> 不是用户逐字原话。**决策本身是用户确认的**（在讨论 block 池与"让大模型生成 block"
> 两条路线的取舍时明确选定了前者并否定后者）。
> 把它写成 🗣 会误导后来者以为这是原话——这里如实标注。

### 2.2 由此推出的结论

**决策模型必须真的在决策，不能沦为装饰。**

| 环节 | 谁决定 | 原语 |
|---|---|---|
| 下一块放什么 | **决策模型** | `choice` |
| 还要不要再来一块 | **决策模型** | `noul` |
| 要几个 | **决策模型** | `numeric` |
| 这结构好不好 | **决策模型** | `score` |
| 这块的具体内容 | 生成层 | LLM / 生图 |

**红线**：生成层**一次都不能决定结构**。

大模型可以**提议**新的 block 类型，但提议必须：
```
生成层提议 → 注册与校验 → 进入 block 池 → 才可能被选中
```
**提议 ≠ 决定。** 这条界线模糊了，项目就退化成"套了个沙盒外壳的聊天机器人"。

### 2.3 为什么这条重要（病根诊断）

用户的原始判断：

> 🗣 **「1，网页模板选取（或者框架布局怎样设计，每个body在哪里，block在哪里）
> 2，素材填充，每个素材对象要怎样实现，用什么实现，为什么
> 3，交互逻辑如何，能否用决策模型作为一个廉价测试对象，模拟用户点击，跑一遍网页
> 4，用户能否参与制作，看到详细流程并随时停止和指导」**

📐 **这四条对应的正是四个缺失的层**：

| # | 缺失 | 本质 | 对应设计稿章节 |
|---|---|---|---|
| 1 | 结构层 | 页面结构藏在 LLM 生成的字符串里，不可决策、不可干预 | §3 |
| 2 | 素材层 | 工具入参只有文本，素材无处安放（"图嵌不进页面"的真实原因） | §3.3 |
| 3 | 验证层 | 沙盒只跑一次性命令，不维持长驻进程，页面跑不起来也就无法验证交互 | §5 |
| 4 | 人在回路 | 一键提交→异步跑完的单向流程，只能看和硬取消，不能指导 | §6 |

**根因一句话**：**工具是"交付物级"粒度**（整页、整篇、整图），下面没有可编排的东西。
所以所有机械（并发、重试、依赖、校验、兜底）都在空转。

🔧 **实测印证**：改造成 block 级粒度后，一个"做网页"的目标从
**1 个节点**（一次大模型调用吐出整个 HTML）变成 **8 个节点**
（6 个 `fill-block` 并发 + 1 个组装 + 1 个校验），
每块可独立重做、可并发、可定点干预。这才是"可编排"的对象。

## 三、产品形态要求

### 3.1 block 候选池（用户主动提出的关键设计）

> 🗣 **「我们可以在每次生成前，提供block候选池（分组），允许由大模型生成更多block加入，
> 或者用户手打/导入block，然后选取需要的block作为候选参与之后的制作。
> 这样的产品就极其优秀了！」**

> 🗣 **「模型提议 + 用户手打 + 导入 属于用户可选项」**

📐 **四类来源**：

```
block 池（按分组组织）
   ├─ 内置 block          ← 我们提供的词表
   ├─ 模型提议的          ← 生成层提议 → 注册校验 → 入池
   ├─ 用户手打的          ← 人工定义
   └─ 导入的              ← 外部来源
        ↓ 用户从池里选取本次要用的
   本次候选集
        ↓
   决策模型在此范围内逐块选择
```

**关键**：后三类是**用户可选项，不是必选项**。
用户不参与时，用内置集合即可跑通全流程——**不能因为"用户没配置"就跑不起来**。

📐 与既有架构同构：现有原则是"候选集来自**工具注册表**，所以扩展工具链 = 改注册表，
不需重训模型"。block 池沿用同一条原则。

### 3.2 模板与沉淀（"越用越好用"）

> 🗣 **「c可以作为一个模板功能，让项目仅限于这个模板内工作，
> 也可以将过去的项目历史生成新模板，作为知识积累，'越用越好用'」**

📐 **模板的两种用法**：

| 用法 | 含义 |
|---|---|
| **限定范围** | 选了模板，本次只在该模板的 block 集合内工作（防跑偏） |
| **起手结构** | 模板给出一个初始 block 序列，可在其上增删改 |

**与现状的关键区别**：现在 `static-page-from-template` 是**把结构硬编码在 TS 里**、且**不可改**。
新设计的模板是**数据**，可改、可派生、可沉淀。

📐 **为什么这是护城河而不是功能**：
跑过的项目留下 结构 + 素材 + 验证结果 的完整痕迹 → 提取可复用结构 → 新模板。
一本字符串形态的 HTML **做不到这一点**（结构藏在文本里，机器读不出来）。

> ⚠️ **前置条件**：沉淀要求持久化。现有 `RunStore` 是内存 `Map`，重启即丢。
> **这条不解决，P8 就是空中楼阁。**
>
> ✅ **2026-10-08 已解决**：运行记录、事件流水、自定义 block 与沉淀的模板都落到 `data/`
> （JSON），启动时读回；交付物也**落定**到 `projects/<项目>/runs/<runId>/`，
> 不再随沙盒回收被删掉。见 [结构化制作链路设计.md](结构化制作链路设计.md) §10.1。
> 上面那句"空中楼阁"的判断仍然成立——它正是这件事必须先做的理由。

### 3.3 素材管理页

> 🗣 **「包括我们应该有素材管理页面（模板、block组件、分组等）」**

📐 四个标签：**模板** / **block 组件** / **分组** / **素材库**。

**与生成前流程的关系**：这个页面就是"block 候选池"的管理界面——
用户在制作前从这里**选取**本次要用的 block。

### 3.4 前端选型

> 🗣 **「我们事实需要更优雅的前端实现方式，例如使用开源的vue框架等」**

📐 **迁移策略必须是"先并存后切换"**，不做原地替换：
1. 新建 Vue 3 前端包，与现有 React 前端**并存**
2. 后端 API 保持不变（REST 契约已稳定）
3. 结构化制作的新功能**只在新前端做**
4. 等新前端覆盖了现有功能，再下线旧前端

理由：重写期间旧界面不可用，会让"随时可演示"这个要求落空。

> 🗣 **「我记得我有要求前端用现成的开源模板例如vue3的社区模板去做，没做吗？」**（追问）

📐 **这条被窄化成了"按 vue-admin 规范自己搭"，而且一行都没写**：`packages/admin`
当时不存在、全仓库 `.vue` 文件数为 0，前端仍是 React。已按"用现成模板"落成：
**pure-admin-thin `v6.2.0`（MIT）**，记为 `packages/admin`，六个页面（工作台 / 结构画布 /
素材管理 / 运行与产物 / 工具目录 / 沙盒），见 [../packages/admin/README.md](../packages/admin/README.md)。

**教训**：把用户的"用开源的 vue 框架"读成"按某套规范手写 Vue 工程"，等于把
**"从成熟模板起手"这个省力意图整个丢掉**。原话里的限定词——"现成的""社区模板"——
不能省略；它们是要求的一部分，不是修饰。

## 四、协作方式的纠正（这一节是我犯错的记录）

### 4.1 用户原话

> 🗣 **「你就没意识到，我是让你报告，而不是让你做？！」**

背景：用户问"什么意思，遇到了什么问题"——那是在**问解释**。
我把它当成了继续动手的许可，接着改了 10 个文件。

> 🗣 **「我问的是，你需要我定的那三条路是什么」**

背景：我上一条汇报里说"三条路需要你定"，但没说清三条路**分别是什么**就追问选择。
用户不得不再问一遍。

> 🗣 **「行吧，继续干活吧 a可以保留」**

背景：这是**明确批准**的样子——指明了做什么（继续干活）、选了什么（A 保留）。

### 4.2 由此推出的结论

**批准的定义（要严格按这个判断）**：

| 算批准 | 不算批准 |
|---|---|
| 在当前对话里说过 | 沉默 |
| **明确指向这件事** | 模糊回应（"嗯"、"哦"） |
| **在动手之前** | 我自己推导出的步骤 |
| | 以前批准过的类似操作 |
| | 用户给了目标之后我自己补的手段 |
| | 任何文档里本来就写着的步骤 |

**一次批准只覆盖它明说的那一步。**

**提问 ≠ 批准。** "这是什么意思"、"遇到了什么问题"、"怎么样了"——
这些都是在**要解释**，不是在**要行动**。

🔧 **执行中的教训**：被纠正后我停下、只报告、把未批准的改动**列出来并说明尚未提交**，
用户随后才决定保留。这个顺序是对的：
**先让用户看到改了什么，再决定留不留**——而不是改完就当既成事实。

### 4.3 报告本身的质量要求

🔧 **教训**：报告要包含**可核对的事实**，不是结论。

一次合格的状态报告应含：

| 要素 | 反例（不合格） | 正例 |
|---|---|---|
| 做了什么 | "修好了" | 改了哪 10 个文件、`onFailure(error, 1)` → `attemptNumber` |
| 验证到什么程度 | "测试通过" | "280 通过 / 1 跳过 / 0 失败"，并说明**什么时候跑的** |
| 不确定的部分 | （略去） | "决策层改动**可能影响 server 测试，尚未重跑**" |
| 未提交的东西 | （不提） | "这些改动全都没有 commit，还在工作区" |

**尤其要主动说明"哪些还没验证"**——把不确定性藏起来，比犯错更糟。

## 五、用户提出的原始关切（接手时的三条）

项目接手时用户明确说了三个"不知道"：

> 🗣 **「1，我不知道代码架构设计情况如何
> 2，我不知道具体逻辑情况如何，是否优雅
> 3，我不知道内聚耦合度如何」**

📐 这三条应作为**交付标准**，而不只是一次性的疑问：

| # | 关切 | 怎么才算回答清楚 |
|---|---|---|
| 1 | 架构设计 | 分层清晰、依赖单向、能画出一张图 |
| 2 | 逻辑优雅 | 有理由的取舍（而不是"能跑就行"），关键决定写进注释 |
| 3 | 内聚耦合 | 可实测：反向依赖数、循环依赖数、声明与用法一致 |

🔧 **本轮的做法**：这三条不是靠"我觉得挺优雅"回答的，而是靠命令核对——
例如"组装器有多少处 `dependsOn`"（→ 证明只支持单链）、
"`numeric`/`score` 在组装器里出现几次"（→ 0 次，证明从未使用）。
**结论必须能复现，否则只是印象。**

## 七、可复用的工作方法（从本项目提炼）

### 7.1 先零成本跑通，再接花钱的层

```
确定性实现跑通全链路 → 测试全绿 → 再考虑接生成层
```
好处：链路形状与成本解耦。接生成层时只替换单个 slot 的实现，不动链路。

### 7.2 结论要能复现

每条断言都配一条命令。示例：

```powershell
pnpm -r test                                    # 测试数
.\scripts\run-structured-demo.ps1               # 零成本跑一次制作
.\scripts\verify-structured-run.ps1 -RunIdPrefix <runId>   # 逐项核对产物
.\scripts\compare-structured-providers.ps1      # 两个 provider 产物一致性
```

### 7.3 "数据/状态/日志全绿但页面是坏的"——这是最危险的一类缺陷

🔧 **本轮的实证**，四个缺陷都属于这一类：

| 缺陷 | 数据层表现 | 只有肉眼才看得见的部分 |
|---|---|---|
| planner 空占位覆盖内容 | `status: filled`、来源 `deterministic`、大小正常 | 图集全是空 `ref`，页面上 5 个破图 |
| 导航项用了长句模板 | 同上，一切正常 | 导航链接 30 多字、折成三行 |
| 品牌名切在词中间 | 同上 | 页面顶部顶着「含首屏、特」 |
| 前端右栏按表单环境判断 | 数据都对 | 看网页运行时右栏是空 preview |

**教训**：验证**不能只看状态字段和产物大小**，必须**看渲染出来的东西**。
补测方向：内容**形态**断言（如"导航项 ≤ 8 字"）、端到端断言产物里的**文本**。

### 7.4 "修了但没生效"——兜底只能有一处

🔧 **实证**：修好 `deriveBrand` 之后页面**纹丝不动**，
因为工具层另写了一份 `goal.slice(0, 16)` 兜底，服务端路径根本不走 `deriveBrand`。

**教训**：同一件事的兜底逻辑写两处，改了 A 忘了 B，表现就是"修了但没生效"。
**兜底必须收敛到一处**，让所有路径都经过它。

### 7.5 环境不兼容要降级，不要判死

🔧 **实证**：实测 rizzo-flow **不支持 `numeric` 原语**（只认 `noul`/`choice`/`score`），
而规划器每遇到带列表的 block 就会问数量 —— 于是**必挂**。

**处理方式**：不是"这个服务不行"，而是**降级**——
把量程切成离散档位，改用 `choice` 问。信息量几乎等价
（"3 项" 与 "中等（3 项左右）" 对结构决策是一回事），而链路照样跑通。

**教训**：能力缺失是常态（不同部署、不同版本）。
遇到不支持的接口，先想**能不能换个等价问法**，再想"要不要放弃"。

### 7.6 无限重试：最贵的一种 bug

🔧 **实证**：`onFailure(error, 1)` 把尝试号写死成 1，
于是 `attempt <= maxRetries` **恒成立**，永远重试、**永不熔断**。
跑满 300 秒、2107 个事件、**0 个产出**。

**教训**：
- 重试计数器必须是**每轮递增**的，不能是常量。
- 状态机要有"有限步内必然走出"的测试——这是能提前抓住它的唯一办法。
- 接了付费端点时，这类 bug 会直接烧钱。

## 八、待用户决策的事项

| # | 事项 | 影响 | 紧急度 |
|---|---|---|---|
| 1 | **持久化方案** —— SQLite / JSON 落盘 / 暂不做 | "越用越好用"（P8）能否成立 | **高**（P8 前置） |

## 九、一句话总结

> **结构由决策模型决定，不由大模型决定；先零成本跑通，再接花钱的层；
> 结论必须能复现；生图要逐次申请。**

违反其中任何一条，都会回到项目最初的那个病根：
**一个巨大的单点，套着沙盒的外壳，所有机械都在空转。**
