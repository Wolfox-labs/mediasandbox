# 两个模型怎么分工，第二种模态怎么加

这份文档回答两个问题，都是**代码里能对上的**，不是设计设想：

1. 一次网页/演示文稿制作里，到底有哪两个模型在干活，各干什么
2. 加一种新模态（这次是演示文稿）要动哪里、不用动哪里

---

## 一、两个模型的分工

```
用户目标
   │
   ├─① 统筹规划 ────────────── 大语言模型（LlmClient，开放生成）
   │      输出：一份内容计划 —— 要讲哪几段、每段讲什么、建议用什么块
   │      落点：packages/orchestrator/src/plan/blueprint.ts
   │
   ├─② 结构决策 ────────────── 决策模型（DecisionClient，封闭问题）
   │      输入：目标 + 计划（作为 facts）+ 当前已排结构 + 候选集
   │      输出：逐轮回答「下一块/页用哪个」「还要不要继续」「要几项」
   │      落点：packages/orchestrator/src/structured/planner.ts
   │
   ├─③ 素材填充 ────────────── 生成层（只有显式开启时才调）
   │      粒度是 **slot**，不是整块：这块标题走确定性、主视觉走生成式，表达得出来
   │      落点：packages/orchestrator/src/structured/filler.ts
   │
   └─④ 组装渲染 ────────────── 确定性代码，不调模型
          网页：renderPage → artifacts/index.html
          文稿：renderDeck → artifacts/deck.html + artifacts/deck.json
```

### 为什么规划不能省

在这之前只有一个模型在"决定结构"：决策模型逐轮答"下一块放什么"。它能选对单块，
但**看不到全局**——不知道这一页要讲几个论点、先后怎么推进，也没有一份可以对着
核对的计划。结果是一堆各自合理的块，而不是一篇讲得通的页面。

规划补的就是这一层。它**不选块**，只写"要讲哪几段"；选哪个块仍然由决策模型的
`choice` 回答。这条边界是刻意的：如果让规划模型直接给出块序列，选结构的人就变成了
生成层，而"生成层决定结构"正是这个项目要消灭的病根。

### 两个模型之间唯一的接口

`blueprintFacts()`（`plan/blueprint.ts`）把计划压成几行文本塞进 `DecisionContext.facts`：

| fact | 内容 |
|---|---|
| `整体规划` | 标题 + 一句话定位 |
| `规划段落数` | 计划里有几段 |
| `规划段落` | `1. 说清这是什么（建议块 hero） \| 2. 证明它好使 \| ...` |
| `目标读者` / `语气` | 模型给的两个补充 |
| `已排块数` | 当前已经排了几块/页 |

刻意只放"计划本身"，不放"我们希望你选 footer"这类暗示——放进去就等于用规划器
替决策层选块。而"规划有没有落下去"由 `describeAlignment()` 算一行对照：

```
计划 3 段，实际 4 块，对得上
计划 3 段，实际 8 块，差 +5
```

这行会进计划的 `rationale`，也会显示在界面上。

### 规划失败怎么办

**不伪造计划。** 规划不可用时（生成层不可达 / 超时 / 返回内容读不出段落）
返回 `{ ok: false, detail }`，`detail` 原样进 `rationale` 与运行记录，界面
照实显示"这次没有统筹规划，原因是……"。编一份假计划比没有更糟——它会让
"计划与实际结构的偏差"这个指标彻底失真。

规划失败**不会**让整次运行失败：生成层不可达不等于页面做不出来。

### 相关开关

| 开关 | 默认 | 说明 |
|---|---|---|
| `useBlueprint: false` | 开 | 关掉统筹规划。用途是对照"有规划和没规划差多少" |
| `blueprintTimeoutMs` | 交给生成层客户端 | 规划超时 |
| `useGenerative` | 工作台固定 **开**；API 缺省**关** | slot 是否交给生成层写。工作台不再提供开关——默认关会让整页变成填充器的元文本；只有走 API 想"零成本只看结构"时才显式传 `false` |

## 二、第二种模态：演示文稿

### 它是新模态，不是"网页改个名"

| | 网页（`webpage`） | 演示文稿（`slides`） |
|---|---|---|
| 单元 | 页面区块（block） | 版式（slide layout） |
| 单元池 | `BUILTIN_BLOCKS` 15 个 | `BUILTIN_SLIDE_LAYOUTS` 8 个 |
| 池的注册表 | `createBlockRegistry()` | `createSlideRegistry()` |
| 分组 | skeleton / content / interactive | deck（单独一组） |
| 一次产出 | 单页长文 | 多页，一页一屏 |
| 中间结构落盘 | `src/blocks/<id>.json` | `src/slides/<id>.json` |
| 产物 | `artifacts/index.html` | `artifacts/deck.html` + `artifacts/deck.json` |
| 渲染器 | `renderPage` | `renderDeck` |
| 工具 | `fill-block` / `assemble-page` | `fill-slide` / `assemble-deck` |
| 截图工具 | `screenshot-page` | `screenshot-deck` |
| 交互验证路径 | `artifacts/index.html` | `artifacts/deck.html` |

### 什么复用了，什么没复用

**复用**（这三层不该为一种新模态重写）：

- `BlockSpec` / `BlockRegistry`：一页幻灯片和一个页面区块在结构上是同一件事
  ——一个有具名 slot 的版式单元
- `StructurePlanner`：逐轮 `choice` 决策的机器一样，只是候选池换了
- `fillBlock`：slot 填充、`numeric` 问句、生成式/确定性分流全都一样
- `PageSpec` / `BlockInstance`：结构留痕与前端展示一样

**没复用**（这些换了就是换了）：

- 渲染器：版面比例、翻页、打印规则、字体单位（`cqw`）都不同
- 两个工具：产物路径、产物形态、校验对象不同
- 版式池：8 个版式与 15 个 block 没有交集，**id 也不许撞**
  （`blocks.test.ts` 里有一条测试守着这件事）

### 产物边界：说清楚它是什么

产出的是**可放映的 16:9 HTML 演示文稿**：

- 直接打开就是全屏放映，方向键 / 空格 / 点左右半屏翻页
- 浏览器「打印 → 另存为 PDF」得到一页一张的 PDF（`@page` 与
  `page-break-after` 已配好）
- 结构另存 `deck.json`，要转别的格式有数据可用

**它不是 .pptx 文件。** 做 .pptx 要在 Node 侧拼 OOXML + ZIP，而这条链路的产物
一律当纯文本写进沙盒，塞二进制进去会让产物收集、校验、下载三处都得改。
与其做一个"文件名是 pptx、打开报错"的东西，不如把能用的做扎实，并把边界写在这里。

### 翻页为什么能直接进交互验证

幻灯片本来就是"一次只显示一页"，它和**标签页**是同一种交互。所以 `renderDeck`
直接复用网页链路那套锚点约定：

```
data-ms-tabs="deck"          ← 页序容器
data-ms-tab="deck:N"         ← 第 N 页的按钮（role="tab"，带 aria-selected）
data-ms-panel="deck:N"       ← 第 N 页的面板（role="tabpanel"）
```

于是 `parseClickTargets` → 决策层挑一个 → `judgeClick` 全都不用改。
这一条不是巧合省事，而是"锚点约定本身就是可复用的接口"的证据。

`verifyInteraction` 为此多了一个 `renderHtml` 参数：演示文稿传 `renderDeck`，
网页用默认的 `renderPage`。**路径与渲染器必须一起换**——只换路径不换渲染器，
结果是解析到 0 个可点元素，看起来像"演示文稿没有交互"。

### 加一种新模态要动的清单

照这次的路走，一共六处：

1. `packages/sandbox/src/types.ts`：`EnvType` 与 `ENV_TYPES` 加一个值
2. `packages/sandbox/src/env-presets.ts`：目录骨架与 requiredCommands
3. `packages/sandbox/src/docker/docker-sandbox.ts`：`IMAGE_BY_ENV` 映射
4. 版式池：一个 `BlockSpec` 数组 + 一个 `createXxxRegistry()`
5. 渲染器 + 两个工具（填一个单元 / 装成一份产物）
6. `plan/assembler.ts` 里一条 `if (envType === 'xxx')` 分支

**不用动的**：决策层、填充器、计划执行器、兜底状态机、结构留痕与前端展示、
统筹规划。这五样之所以不用动，是因为它们的数据形态是 `PageSpec`，
与"这个模态长什么样"无关。

## 三、验证

```powershell
# 编排层（含统筹规划与演示文稿渲染器）
cd packages\orchestrator
..\..\node_modules\.bin\tsc.cmd -p tsconfig.json
node --test "dist/**/*.test.js"

# 服务层（含两条链路的端到端）
cd packages\server
..\..\node_modules\.bin\tsc.cmd -p tsconfig.json
node --test "dist/**/*.test.js"
```

关键用例：

| 用例 | 断言的是什么 |
|---|---|
| `orchestrator/dist/plan/blueprint.test.js` | JSON / 散文 / 失败三条解析路径；计划压成 facts；对齐算法 |
| `server/dist/blueprint.test.js` | 规划是**一次独立的生成层调用**，计划出现在运行详情与 `plan_assembled` 里；关掉时如实写"被关掉了"；规划失败不拖垮运行 |
| `server/dist/deck.test.js` | 多页、每页有版式、翻页锚点齐全、打印一页一张、不引用外部资源、两个池子不串、未知版式被拒 |
| `orchestrator/dist/structured/blocks.test.js` | 网页池里没有 deck 组；版式池与 block 池的 id 不撞 |
