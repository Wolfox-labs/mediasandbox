## 1. 项目定位

Web 端的 Agent 沙盒平台。用户给出一个创作目标（"做一个网页"、"做一个 App"、"做一套产品图"），平台完成三件事：

1. **排布**：决定用哪些工具、哪些技术栈、工具链按什么顺序串。
2. **执行**：在隔离容器里逐步执行，产出可运行的文件。
3. **预览**：在网页里直接看到结果。

"排布"由本地运行的 Jev 类决策模型负责，"执行"由通用大模型负责。

### 1.1 职责分界

| 环节 | 由谁做 | 输出形式 |
|---|---|---|
| 目标分类、技术栈选择、工具链排布、单步成败判定、重试决策 | 本地 Jev 类模型 | 封闭选项上的选择 + 概率 |
| 写代码、写文案、生成图片、生成视频 | 第三方通用大模型 | 自由文本 / 二进制 |
| 步骤 DAG 组装、重试上限、超时、熔断、降级 | 确定性代码（状态机） | 程序结构 |

**决策模型只回答"选哪个"，不生成任何文本。** 计划 DAG 由确定性代码按模型的选择结果拼装，因此不存在模型输出格式错误的问题。

## 2. 系统架构

```
┌──────────────────────────────────────────────────────────┐
│ 前端交互层  React 18 + Vite + Tailwind                    │
│  Agent 工作台 │ 沙盒控制台 │ 实时预览 │ 项目管理            │
└───────────────────────────┬──────────────────────────────┘
                            │ HTTP + WebSocket
┌───────────────────────────▼──────────────────────────────┐
│ 服务调度层  Node.js + Express + Socket.IO                  │
│  会话上下文 │ 任务队列 │ 进度推送 │ 权限校验                │
└──────────┬────────────────────────────┬──────────────────┘
           │                            │
┌──────────▼──────────────┐  ┌──────────▼──────────────────┐
│ 决策层  Python FastAPI   │  │ 生成层  第三方多模态 API      │
│  rizzo-flow（Jev 类）    │  │  通用 LLM 执行具体生成        │
│  ├ 工具注册表            │  │  文本 / 图像 / 视频 / 代码    │
│  ├ /v1/systemone 调用    │  └─────────────────────────────┘
│  ├ 选型决策（choice）    │
│  └ 成败判定（noul/score）│
└──────────┬──────────────┘
           │ Docker API
┌──────────▼──────────────────────────────────────────────┐
│ 沙盒执行层  Docker 容器（每项目一个）                     │
│  预置工具链镜像 │ 网络限制 │ 文件边界 │ 资源配额           │
│  容器内运行通用 LLM 生成的代码                            │
└─────────────────────────────────────────────────────────┘
```

### 2.1 各层职责

**前端交互层**：对话输入与步骤流展示；容器启停与资源监控；网页、图片、脚本产物的渲染；项目文件与模板管理。

**服务调度层**：会话上下文维护；任务队列；执行进度实时推送；请求权限校验。该层不承担决策逻辑，也不承担内容生成。

**决策层**：持有工具注册表；向本地模型发起 `choice` / `noul` / `score` / `numeric` 提问；按模型返回的选择结果组装执行 DAG。模型与服务同机运行。

**生成层**：调用第三方多模态大模型完成具体的文本、图像、视频、代码生成。产物直接写入项目目录。

**沙盒执行层**：每个项目一个独立容器；容器内预置数字媒体工具链；执行通用 LLM 生成的代码；网络、文件系统、CPU 与内存均受约束。

## 3. 调度层设计

### 3.1 决策模型

选用 **rizzo-flow**。它是 Rizzo AI Academy 的开源项目，复现了 Jev（TypeSafe AI 的 System One 模型）的接口模式。

工作方式：给一段状态（state）和若干问题，模型做**一次前向传播**，只在最后一个位置读取候选答案字母的 logits，softmax 之后得到带概率的答案。**不生成任何 token**，因此不会出现格式错误，单次决策约 50 毫秒。

四类原语：

| 原语 | 用途 | 本项目中的用途 |
|---|---|---|
| `noul` | 是/否 | 某步是否成功、是否需要人工介入 |
| `choice` | 多选一 | 选技术栈、选工具、选执行路径 |
| `score` | 按评分标准打分 | 给产出质量打分 |
| `numeric` | 数值 | 估算步骤数、耗时 |

### 3.2 排布流程

以"我要做一个网页"为例：

```
用户目标
   │
   ├─ [choice] 目标类型 → 网页应用 / 移动应用 / 图像作品 / 视频作品 / 文案
   │
   ├─ [choice] 技术栈   → 候选项由工具注册表按目标类型筛出
   │
   ├─ [choice] 构建工具 → 同上
   │
   ├─ [choice] 样式方案 → 同上
   │
   ├─ [numeric] 预估步骤数
   │
   └─ 确定性代码按选择结果拼装 DAG
              │
              ▼
        通用 LLM 逐步执行 → 容器内产出文件 → 预览
              │
              ├─ [noul]  该步是否成功
              ├─ [score] 产出质量
              └─ 确定性状态机决定：重试 / 换方案 / 熔断
```

**模型在每个环节只回答一个封闭问题**，候选集合来自工具注册表。这样避免了小模型生成多步计划时的漏步、环依赖问题，也省去了对模型输出的解析。

### 3.3 工具注册表

工具注册表是决策层的核心数据结构，描述"有哪些工具可用、各自适合什么场景"。

```json
{
  "tools": [
    {
      "id": "vite",
      "category": "build",
      "applies_to": ["web"],
      "label": "Vite 构建工具",
      "description": "面向现代浏览器的快速构建工具，适合单页应用"
    }
  ]
}
```

发 `choice` 问题时，系统按当前目标类型过滤出候选，把 `label` 作为选项交给模型。**扩充工具链只需改注册表，不需重训模型**——这是该设计可维护的前提。

### 3.4 失败兜底

兜底**不使用模型**，用确定性状态机：

| 情况 | 处理 |
|---|---|
| 单步失败 | 重试，上限 3 次 |
| 连续失败 | 回到上一个决策点，换一个技术栈选项重跑 |
| 换方案仍失败 | 熔断，标记该步骤为需人工介入 |
| 单步超时 | 按配置终止容器内进程 |

理由：兜底逻辑本身不能依赖概率模型，否则模型判断失误时会发生二次失败。

### 3.5 两套权重方案

调度模型有两种来源，都保留，通过配置切换。

| 方案 | 权重 | 体积 | 准确率 | KL↓ | Brier↓ | ECE↓ |
|---|---|---|---|---|---|---|
| **A：用官方训练好的** | Rizzo Flow 4B Q4_K_M | **2.6 GB** | **0.650** | 0.436 | 0.201 | 0.093 |
| A：用官方训练好的 | Rizzo Flow 4B Q8_0 | 4.4 GB | 0.648 | 0.452 | 0.205 | 0.112 |
| A：用官方训练好的 | Rizzo Flow 1.7B Q8_0 | 1.8 GB | 0.544 | 0.694 | 0.275 | 0.169 |
| **B：我们自己训练的** | 自训 1.7B LoRA | 待定 | 待测 | 待测 | 待测 | 待测 |
| 对照：未微调底座 | Spark-X2.5-4B 原始 | 4.4 GB | 0.574 | 2.899 | 0.480 | 0.349 |
| 对照：云端本体 | TypeSafe Jev 1.13.0 | 托管 | 0.727 | 1.442 | 0.148 | — |

数据来源为 rizzo-flow 官方在 `typed-decisions` 基准上的公布值（400 用例、2000 个决策，Q8_0，同机测量）。TypeSafe Jev 一行取自其官方数据集卡片，未经复测。

**方案 A 的默认选择是 4B Q4_K_M**：相比 Q8_0 体积减半而准确率持平（0.650 对 0.648），相比 1.7B 高约 10 个百分点。

**方案 B 见第 6 节。**

## 4. 技术栈

| 层 | 选型 | 理由 |
|---|---|---|
| 前端 | React 18 + Vite + Tailwind CSS | 组件生态成熟，构建快，样式方案可控 |
| 后端网关 | Node.js + Express + Socket.IO | 长连接实时推送执行步骤与中间结果 |
| 决策服务 | Python 3.12 + FastAPI + rizzo-flow | rizzo-flow 是 Python 项目；后训练用 PyTorch / PEFT，同为 Python 生态 |
| 推理运行时 | llama.cpp | llama.cpp 本身做得好：GGUF 生态完整、量化方案成熟、后端覆盖 CUDA / Vulkan / Metal / ROCm / CPU，可复用同一套权重跨平台部署 |
| 沙盒 | Docker 容器 | 每项目独立容器，配合资源与网络限制 |
| 生成 | 第三方多模态大模型 API | 文本 / 图像 / 视频 / 代码 |

## 5. 功能模块

### 5.1 Agent 创作工作台

对话式输入，多轮上下文。展示每一步的决策结果（选了哪个工具、概率多少）、执行状态、中间产物。决策过程可见是该平台区别于普通聊天框的地方。

### 5.2 沙盒环境管理

一键启动 / 重置容器，环境分类（前端 / 图像 / 文案），资源占用监控。容器配置包括网络限制、文件边界、CPU 与内存配额。

### 5.3 实时预览

网页用 iframe 直接预览；图片在线查看；脚本输出按类型渲染。

### 5.4 项目与模板

文件树管理、成果导出、内置数字媒体创作模板（模板同时充当决策层的默认选型起点）。

## 6. 后训练

### 6.1 目标

在 rizzo-flow 的机制上再做一层针对"数字媒体工具排布"的 LoRA 微调，作为方案 B 的权重。

### 6.2 机制

rizzo-flow 的训练方式与推理完全一致：同一个 prompt 编译函数，同一次前向传播，只在答案字母位置上计算**软交叉熵损失**，只更新 LoRA 适配器。不监督任何其他 token，不训练模型"写文本"，只训练它"把概率分配给正确的选项"。

官方训练脚本在 `training/` 目录下：`download_data.py`、`build_data.py`、`train_lora.py`、`export_gguf.py`、`smoke_parity.py`、`check_batching.py`。微调目标模型由环境变量 `RIZZO_TRAIN_SIZE` 指定，可选 `4b` 或 `1.7b`。

### 6.3 数据

| 来源 | 说明 |
|---|---|
| `tasksource/procedural-typed-decisions` | 公开程序化生成数据 |
| `ZefanCai/Open-Jev` | 公开数据，取 `release-v2-redistributable` |
| `Praveenrajus/jev-bench` | 12 个配置 |
| 自建 | 数字媒体工具排布问答：给出创作目标，标注正确的技术栈与工具链选择 |

rizzo-flow 官方用 28,321 个问题完成训练。自建部分是本次训练相对官方的增量。

### 6.4 评估

复用官方基准 `LocalLLaMA/typed-decisions` 与官方脚本 `scripts/typed_decisions.py`，输出准确率、KL、Brier、ECE 四项指标，与方案 A 及未微调底座横向对比。

### 6.5 导出与部署

训练完成后经 `export_gguf.py` 融合适配器并转换为 GGUF，交由 llama.cpp 加载，与方案 A 的权重共用同一套推理路径。
