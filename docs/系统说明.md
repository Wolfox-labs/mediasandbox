# MediaSandbox 系统说明

> 本文面向评审与验收，回答四个问题：**它是什么、怎么用、怎么做的、怎么验证的。**
> 技术细节见 [`架构说明.md`](架构说明.md)（实现与踩坑）与
> [`架构与业务逻辑.md`](架构与业务逻辑.md)（与设计蓝图的逐条对照）。

## 一、这是什么

**一个通用 Agent 沙盒平台。** 用户给一个创作目标，系统自己完成三件事：

```
目标 → 决策层选工具 → 确定性代码拼 DAG → 沙盒里执行 → 生成内容 → 产物
```

与普通对话式 AI 的关键区别：**决策过程可见**。系统不只是一个聊天框，
它把"为什么选这个工具、每一步什么状态、失败了怎么兜底"全部摊开给人看。

### 职责分界（这是设计地基）

| 层 | 由谁做 | 做什么 |
|---|---|---|
| 决策层 | 本地 Jev 类模型 | **只回答封闭问题**：选哪个工具、要不要校验、怎么收尾 |
| 编排层 | **确定性代码** | 把答案组装成 DAG 并执行。不调用模型做规划 |
| 生成层 | 第三方多模态 API | 真正生成文本 / 图像 / 代码 |
| 执行层 | 沙盒 | 隔离运行，管控网络、文件、资源 |

**关键约束**：决策层模型**不生成文本、不产出自由形式的计划**。它只在有限候选集里
选一个值。把答案拼成执行流程是确定性代码的活 —— 这保证了行为可复现、可测试、可兜底。

## 二、怎么用

### 2.1 启动

需要 **Node ≥ 24** 与 **pnpm ≥ 11**。

```bash
pnpm install
pnpm -r build          # 构建三个后端包 + 前端
cp .env.example .env   # 按需填写（见下）
pnpm start             # → http://127.0.0.1:8787/
```

打开浏览器即可。**前端由后端一并托管，所以只有一个地址**，不需要另起前端服务，
也没有 CORS 问题。

### 2.2 环境变量

全部变量见 [`.env.example`](.env.example)。最关键的三个：

| 变量 | 默认 | 说明 |
|---|---|---|
| `MEDIASANDBOX_DECISION` | `demo` | `demo` 演示决策层 / `stub` 固定桩 / `rizzo` 真实模型 |
| `LLM_API_KEY` + `LLM_BASE_URL` + `LLM_MODEL` | 空 | 生成层（文本）。**不配则只能走确定性路线**（产物为占位文本） |
| `LLM_IMAGE_BASE_URL` + `LLM_IMAGE_API_KEY` + `LLM_IMAGE_MODEL` | 空 | 生成层（图像）。可指向**另一个服务商**；不配则 `render-image` 回落到文本补全 |
| `SANDBOX_PROVIDER` | `local` | `local` 路径级隔离 / `docker` 容器级隔离 |

> **文本与图像可以是两个不同的端点。** 实际部署里两者常来自不同服务商
> （不同域名、不同密钥），这时用 `SplitLlmClient` 组合两个客户端即可，
> 不必把两套凭据塞进一个客户端。

### 2.3 四种运行模式

| 模式 | 配置 | 用途 |
|---|---|---|
| **纯离线演示** | `MEDIASANDBOX_DECISION=stub`，不配 LLM | 无任何外部依赖，跑通全链路（产物是占位文本） |
| **演示模式**（默认） | `MEDIASANDBOX_DECISION=demo` + 配 LLM | 关键词选工具 + 真实内容生成 |
| **接真实决策模型** | `MEDIASANDBOX_DECISION=rizzo` | 需先部署 rizzo-flow（见 §5） |
| **容器隔离** | `SANDBOX_PROVIDER=docker` | 跑不可信代码时用 |

### 2.4 界面导览

启动后顶部有三个标签页：

| 标签 | 内容 |
|---|---|
| **创作工作台** | 左：输入目标 + 运行历史；中：决策过程 + 执行步骤；右：实时预览 |
| **项目与产物** | 项目维度的文件树、导出 ZIP、内置模板 |
| **沙盒环境** | 运行概况、两个 provider 的能力对比、容器隔离的 8 项约束、三类环境预设 |
| **工具链** | 决策层的候选集 —— 每个工具的环境、角色、输入输出端口 |

> **工作台与项目页的区别是视角**：工作台盯"这一次运行"的过程，
> 项目页盯"我这个项目攒下了什么"。一个项目可能跑过多次
> （重试、换方案、改目标重来），产物要按项目归到一起看。

工作台操作流程：

1. 左侧输入创作目标（或点示例），选环境类型（文案 / 图像 / 前端）
2. 点「开始创作」→ 提交后立刻返回，执行是异步的
3. 中间栏实时显示：**决策过程**（选了哪个工具、组装依据、重试与换方案）
   与**执行步骤**（按依赖分层，同层标注并发数）
4. 右栏在产物生成后自动可预览：网页走 iframe、图片走 img、文本给双视图

### 2.5 REST API

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/health` | 决策层 + 生成层探活、可用 provider、工具数 |
| GET | `/api/tools` | 工具清单（含输入输出端口），可按 `?envType=` 筛 |
| POST | `/api/runs` | 提交运行 → **202 + runId** |
| GET | `/api/runs` | 列出运行记录 |
| GET | `/api/projects` | **项目维度视图**（运行按 `projectId` 分组） |
| GET | `/api/projects/:id/export` | **导出项目产物为 ZIP** |
| GET | `/api/runs/:id` | 查状态（含 attempts / reason / planSummary） |
| GET | `/api/runs/:id/artifacts` | 产物清单 |
| GET | `/api/runs/:id/artifacts/:name` | 下载产物字节 |
| POST | `/api/runs/:id/cancel` | 取消 |

WebSocket：`ws://host:port/ws?runId=<可选>`。

```bash
curl -X POST http://127.0.0.1:8787/api/runs \
  -H 'content-type: application/json' \
  -d '{"goal":"写一段产品介绍","envType":"copy"}'
# → {"runId":"run-...","status":"queued"}
```

## 三、技术架构

### 3.1 分层

四个包，一条**单向**依赖链（已逐文件核实，无反向 import、无循环依赖）：

```
packages/web          ← 前端（React 18 + Vite + Tailwind）
packages/server       ← HTTP + WebSocket，托管前端产物
    ├── packages/orchestrator
    │       └── packages/sandbox
    └── packages/sandbox
```

| 包 | 行数 | 职责 |
|---|---:|---|
| `sandbox` | 1476 | 沙盒抽象 + Local/Docker 两个实现 |
| `orchestrator` | 4632 | 决策层契约、工具注册表、DAG 组装与执行、兜底状态机 |
| `server` | 1025 | REST + WebSocket，不做编排决策；含自写 ZIP 写入器 |
| `web` | 2374 | 四个界面模块 |

### 3.2 两个核心抽象

**`SandboxProvider`** —— 10 个方法，两个实现可互换：

| | LocalSandbox | DockerSandbox |
|---|---|---|
| 隔离强度 | 路径级 | 容器级 |
| 网络 | 不限制 | `none`（没有网卡） |
| 文件 | 目录边界 + 符号链接校验 | 只挂载工作区 |
| 资源 | 无 | 内存 512MB / CPU 1核 / PID 256 |
| 根文件系统 | — | 只读 |
| 降权 | — | uid 1000、CapDrop ALL、no-new-privileges |
| 用途 | 开发、测试、降级 | 执行不可信代码 |

**"适配完成"的定义**：同一套 18 项一致性套件在两个实现上**都全绿**。

**`DecisionClient`** —— 对接 rizzo-flow 的 `POST /v1/systemone`，四类原语：

| 原语 | 用途 | 本系统用了吗 |
|---|---|---|
| `noul` | 二值判定 | 用了（`needs_verify` / `needs_refine`） |
| `choice` | 有限选项单选 | 用了（`primary_tool` / `finalize`） |
| `score` | 标量打分 | 实现了，未使用（纯储备） |
| `numeric` | 数值估计 | 实现了，未使用（步骤数由确定性代码算） |

三个设计要点：

1. **批量是主接口**。一次请求带多个问题共享同一次 prefill
2. **弃权是合法输入**。模型答"不知道"时按确定性默认继续，**不当错误**
3. **候选集来自工具注册表**。所以扩展工具链 = 改注册表，**不需要重训模型**

### 3.3 兜底策略（确定性，不用模型）

```
执行失败 → 重试（≤3 次） → 换方案（≤1 次） → 熔断转人工
```

**刻意不用概率模型**：兜底逻辑若依赖模型，就会在失败时二次失败 ——
而它存在的意义正是在事情已经出错时可靠地做决定。

失败被分成 6 类（`plan` / `tool` / `decision_unavailable` / `transient` /
`unknown` / `abstained`），不同类走不同路径。归类**按异常类型**判断，
不靠正则匹配错误消息 —— 后者一旦改措辞就会静默退化。

### 3.4 三个环境与工具链

每类环境都提供**两条路线**，这是刻意设计：有两条，`choice` 才有真实的选择可做；
而且生成层不可用时，确定性路线就是降级方案。

| 环境 | 生成式（调模型） | 确定性（不调模型） | 收尾 |
|---|---|---|---|
| `copy` | `draft-copy` | `template-copy` | `write-file` |
| `image` | `render-image` | `solid-image` | *(无)* |
| `frontend` | `scaffold-frontend` | `static-page-from-template` | `build-frontend` |
| 通用 | — | `write-file` / `process-image` / `verify-artifact` / `refine-copy` | |

**组装器实际发 4 个问题**（全是 `choice` 与 `noul`）：

| 问题 | 类型 | 何时发 |
|---|---|---|
| `primary_tool` | choice | 主产出候选 ≥ 2 个时 |
| `needs_refine` | noul | 候选里含 `draft-copy` 时 |
| `finalize` | choice | 收尾候选 ≥ 2 个时 |
| `needs_verify` | noul | 总是 |

## 四、测试与验证

### 4.1 怎么跑

```bash
pnpm -r typecheck
pnpm -r test
```

### 4.2 覆盖情况

**204 项测试，0 失败**（1 项按环境如实跳过）。

| 包 | 项数 | 覆盖 |
|---|---:|---|
| sandbox | 49 | provider 一致性 18 项 × 两个实现、容器隔离约束、产物判定 |
| orchestrator | 129 | 决策契约、注册表、组装器、执行器、兜底、LLM 客户端（含图像端点）、端到端 |
| server | 26 | REST、WebSocket、双 provider 一致性、沙盒保留策略、ZIP 写入器 |
| web | — | 通过 typecheck 与端到端实跑验证 |

### 4.3 几个刻意设计的测试

- **契约测试**：一套用例跑遍所有实现。任何一边挂掉，说明抽象漏了。
- **环境缺失如实跳过**：例如宿主 `python` 是 WindowsApps 存根时，相关用例
  `skip` 并说明原因，**不假装通过**。
- **双 provider 产物一致性**：同一目标在 Local 与 Docker 上产出的文件
  **SHA-256 逐字节相同**。这是沙盒抽象成立与否的最终验收。
- **穷举回归**：`envType × 主产出 × 打磨 × 收尾` 共 54 种组合全部组装并校验，
  任一组合出现非法端口引用即失败。

### 4.4 隔离约束的验证方式

DockerSandbox 的每条约束都有对应用例实际探测，不是读配置推断：

| 约束 | 怎么验的 |
|---|---|
| 无网络 | 容器内尝试连接 `1.1.1.1:80`，断言收到 `NO_NET` |
| 根文件系统只读 | `touch /etc/should-fail`，断言非零退出 |
| 非 root | `id -u`，断言输出 `1000` |
| 内存超限被 kill | 循环申请 64MB 块，断言进程被内核终止 |
| 超时终止整棵进程树 | 起子进程后超时，断言子进程不留活口 |

## 五、接真实决策模型（可选）

系统默认跑**演示决策层**（按目标关键词选工具），无需任何模型即可完整运行。
要接真实的 Jev 类决策模型：

```bash
git clone https://github.com/Rizzo-AI-Academy/rizzo-flow
cd rizzo-flow
uv sync --locked
uv run rizzo download --size 4b --quant q4_k_m   # 注意默认拉的是 Q8_0
uv run rizzo serve                                # → http://127.0.0.1:8017
```

然后把 `MEDIASANDBOX_DECISION` 改成 `rizzo`。后端只需改这一个环境变量，
**上层代码零改动** —— 因为 `RizzoFlowClient` 与演示决策层实现的是同一个接口。

> **合规声明**：本项目使用 [rizzo-flow](https://github.com/Rizzo-AI-Academy/rizzo-flow)
> （Apache-2.0），这是一个**独立的第三方开源项目，与 TypeSafe 无关联**。
> 其权重底座为 **Spark-X2.5**，**并非 TypeSafe Jev 的官方权重**。
> "Jev" 与 "TypeSafe" 商标归 TypeSafe 所有。

## 六、已知限制

| 项 | 说明 |
|---|---|
| **目标分类未实现** | `envType` 由调用方在请求里指定，决策层没参与"这是什么类型的任务"的判断 |
| `score` / `numeric` | 实现了但从未被使用，是纯储备代码 |
| 宿主 `python` | 本机 `python` 指向 WindowsApps 存根，`solid-image` 在 Local provider 下不可用；容器内是真的 |
| 图像生成 | 依赖生成层是否提供图像模型。拿不到图像数据时**如实失败**，不产出伪装成图片的文本 |
| 无持久化 | 运行记录在内存里，重启后丢失；沙盒句柄需重新 `adopt()` |
| 无队列 | 多个请求并发执行，无上限 |
| 单实例 | 未做多实例部署 |
| Docker exec 流分离 | 按多路复用帧格式解帧。若容器分配 TTY，帧格式不同，当前实现不处理 |
