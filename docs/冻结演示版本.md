## 一、启动（两条命令）

```bash
cd MediaSandbox
pnpm install && pnpm -r build
pnpm start            # → http://127.0.0.1:8787/
```

演示前请确认 Docker Desktop 已启动：截图与模拟点击都靠**旁挂 chromium 容器**，
Docker 不在时服务仍能跑，但截图会退化成占位图（启动日志里会写明是哪一个）。

启动日志就是第一份验收单，逐行对应现实：

```
[mediasandbox] 决策层：演示模式（关键词判断，非真实模型；MEDIASANDBOX_DECISION=rizzo 可切真实模型）
[mediasandbox] 截图      chromium（旁挂容器渲染沙盒里的页面，镜像 mediasandbox/browser:latest）
[mediasandbox] 保留      20 个已结束运行的沙盒（SANDBOX_RETENTION 可调，0 = 不保留）
[mediasandbox] 落定保留  不清理（交付物一个都不删，PROJECTS_RETENTION 可调）
```

**演示不需要任何外部模型**：决策层默认走内置演示层，生成层未配置时
确定性填充照常工作——这正是"零成本降级"那条设计。

## 二、冒烟：一条命令证明链路还活着

服务起着的时候，另开一个终端：

```bash
node packages/server/probe-server-demo.mjs
```

它走的是**真 HTTP API**（不是直接调库）：健康检查 → 提交一次结构化运行 →
等结束 → 逐个下载产物并核对大小 → 校验截图是不是真 PNG（魔数 + 尺寸）。
期望输出：

```
✓ 服务健康 {...}
✓ 已提交运行 run-...
✓ 运行成功，产出 2 个产物
✓ artifacts/index.html 11656B
✓ artifacts/screenshot.png 108114B
✓ 截图是真 PNG：1280x800，108114B
```

任何一步不对就非 0 退出并打印实际拿到的东西——它不会"看起来成功了"。

## 四、已知缺口（这一版**没有**的东西）

1. **并发上限与队列**：同一时刻的并行运行没有全局上限，也没有排队/背压。提案见本文件的下一节。
2. **生成式能力**：未配 `LLM_API_KEY` 时不可用（这是设计里的降级路线，不是缺陷）；
   配了之后才会走真实生成模型。
3. **文档有几处已经和实现对不上**（本次**未**改动，列在这里以免被当成现状）：
   - `README.md`、`docs/系统说明.md` 里仍写着结构化链路"落成占位块"；
   - `docs/结构化制作链路设计.md` 里 P5（浏览器驱动）标着"未开始"，实际已经跑通；
   - `docs/用户要求与协作经验.md` 里关于截图/点击的描述早于本次改动。
4. **浏览器点击驱动的隔离让步**：CDP 要连容器端口，而 `network=none` 下 Docker
   不允许发布端口，所以点击驱动用 bridge 且端口**只绑 127.0.0.1**；
   截图驱动仍是 `network=none`。这条写在 `packages/orchestrator/src/render/chromium-click.ts` 文件头。

## 五、下一步（待批准，尚未动手）

**B-D2：并发上限与队列**。提案要点：

- 现状：每次 POST `/api/runs` 都直接起一次运行，没有全局上限。演示时点几下没问题，
  但批量提交会把 CPU / 内存 / 容器数一起推上去（Docker 下每个运行一个容器）。
- 提议：`maxConcurrentRuns`（默认取一个保守值，例如 2）+ 一个**有界队列**（例如 16）。
  超出队列长度直接 **429**（明确拒绝，而不是默默堆积）。
- 关键取舍：排队中的运行状态要能被界面看见（`queued` + 队列位置），否则用户会以为卡死；
  队列在进程重启后**不恢复**（宁可让人重新提交，也不要做"幽灵运行"）。
- 需要你确认的点：默认并发数取多少、队列满了是 429 还是继续排队。
