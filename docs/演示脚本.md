# 功能演示脚本

> 按本文顺序操作，可在 5 分钟内走完一遍完整流程。
> 每一步都标注了**该看到什么**，便于录制演示视频或现场答辩时对照。

---

## 演示前准备

### 1. 启动服务

一条命令进入可演示状态（起服务 + 跑冒烟 + 打印"该看到什么"）：

```bash
cd MediaSandbox
pnpm install && pnpm -r build
node scripts/demo.mjs          # 跑完自动停；--keep 留在前台
```

或者手动两步：

```bash
cp .env.example .env      # 按需填写生成层 key
pnpm start                # → http://127.0.0.1:8787/
```

浏览器打开 <http://127.0.0.1:8787/>，应看到顶部四个标签页与右上角状态徽标。

**右上角状态徽标**是第一个看点，它一眼说明链路通不通：

| 徽标 | 含义 |
|---|---|
| 决策层 就绪 | 决策服务可达（真实 rizzo 或演示层） |
| 生成层 就绪 | 生成端点可达；显示"未配置"则只能走确定性路线 |
| local | 当前沙盒 provider |

### 2. 若接了真实 rizzo-flow，先热身

> **这一步不能省。** 首次请求要 30 秒以上（模型加载 + prefill），
> 之后同前缀请求复用 KV cache 降到亚秒级。演示前先跑一次，
> 否则第一次点击会干等半分钟。

```bash
curl -X POST http://127.0.0.1:8017/v1/systemone \
  -H 'content-type: application/json' \
  -d '{"state":"warmup","model":"rizzo-latest","questions":{"q":{"type":"noul","instructions":"warmup"}}}'
```

## 演示动线（五站）

### 第一站：创作工作台 —— 看"决策过程"

**操作**：在「创作目标」输入 `做一个产品介绍落地页，含标题、特性列表和页脚`，
环境选「前端 / 网页」，点「开始创作」。

**该看到什么**：

1. 提交后**立刻返回**（202），不是等执行完才响应 —— 执行是异步的
2. 「决策过程」面板逐条出现**组装依据**：
   ```
   主产出工具：scaffold-frontend
   决策层要求校验，追加 verify-artifact
   收尾工具：build-frontend
   ```
3. 「执行步骤」按**依赖分层**展示，同层标注"并发 N 个"
4. 右上角「实时通道 已连接」表示 WebSocket 事件流正常

**讲解点**：这就是本项目区别于普通聊天框的地方 —— 普通 AI 只给结果，
这里把"选了哪个工具、为什么选、每步什么状态"摊开给人看。

**一个值得单独指出的细节**：如果决策层要求"打磨文案"，但主产出是页面
（没有文案产出），依据里会出现：

```
决策层要求打磨，但 static-page-from-template 没有文案产出，跳过 refine-copy
```

这是组装器**识别出该节点接不上、主动跳过**，而不是插一个必然失败的节点。

### 第二站：实时预览 —— 看产物

**操作**：等运行成功，右侧「实时预览」自动出现页面。

**该看到什么**：

1. 网页在 iframe 里**直接渲染**，可滚动、样式完整
2. 顶部可切「渲染 / 源码」两种视图
3. 若有多个产物，顶部出现切换按钮

**讲解点**：预览用的是 `sandbox="allow-scripts"` 的 iframe，
**产物里的脚本碰不到工作台上下文** —— 跑的是模型生成的不可信代码，
这一点必须隔离。内容也是 fetch 回来后再注入，而不是让 iframe 直接
指向下载地址（那样产物页面会拿到 `/api` 的同源上下文）。

### 第三站：交互验证 —— 让它自己点一下（W2）

> **这一站需要 Docker**（旁挂 chromium 容器）。没有 Docker 时不要跳过这一站，
> 而是**当作一个看点来讲**：界面上的「交互验证」按钮会如实回 503 并说明原因——
> "没验证就说没验证"，比给一个灰色的"通过"更值得展示。

**操作**：在第二站那次成功运行的页面上，中栏找到「交互验证」面板，点「交互验证」。

**该看到什么**：

1. 按钮变成「正在点…」（3–10 秒：起容器、渲染、点击、比对快照）
2. 结论徽标是**三种之一**，不是笼统的"成功/失败"：

   | 徽标 | 含义 |
   |---|---|
   | 通过 | 点到了，且观察到了"该发生的变化" |
   | 未通过 | 点了但没变化——下面列出尝试记录（点了哪个、为什么不算） |
   | 未做验证 | 页面上没有可点元素。**这既不是通过也不是失败** |

3. 结论下方是**代码给出的判定**与人话总结，以及「点击后截图 artifacts/click.png」链接

**讲解点**：判定由代码做出（`judgeClick`），**不采信模型的说法**——
模型只负责"挑一个最值得点的元素"，而"点完算不算成功"是确定性判断。
这两件事分开，是这套系统里"LLM 判断、代码执行"那条地基的又一次落地。

**为什么是按钮触发而不是自动跑**：这一步要起真浏览器，耗时 3–10 秒，
而大多数运行并不需要它。自动跑等于给每次运行都加上这段开销。

### 第四站：项目与产物 —— 看"攒下了什么"

**操作**：切到「项目与产物」标签。

**该看到什么**：

1. 左栏项目列表，每个项目显示运行次数与产物数
2. 中栏**文件树按运行分组** —— 同一项目跑两次，两个 `index.html` 各占一个目录
3. 点「导出 ZIP」下载整包

**讲解点**：工作台盯"这一次运行"，项目页盯"这个项目攒下了什么"。
一个项目可能跑过多次（重试、换方案、改目标重来），产物要归到一起看。
导出包里带 run 前缀正是为此 —— 否则同名产物会互相覆盖。

**可现场验证导出包**：

```powershell
Expand-Archive -Path "$env:USERPROFILE\Downloads\proj-xxx.zip" -DestinationPath .\out
Get-ChildItem -Recurse .\out
```

### 第五站：沙盒环境 / 工具链 —— 看"隔离做了什么"

**操作**：切到「沙盒环境」，再切到「工具链」。

**该看到什么（沙盒环境）**：

- 两个 provider 的能力对比（路径级 vs 容器级）
- **容器隔离的 8 项约束**，每条带"为什么"：
  网络 `none`、根文件系统只读、uid 1000、CapDrop ALL、
  no-new-privileges、内存 512MB、CPU 1 核、PID 256
- 三类环境预设的目录骨架与镜像大小

**该看到什么（工具链）**：

- 决策层的候选集，每个工具的**输入输出端口**
- 每类环境的**两条路线**：生成式（调模型）与确定性（不调模型）

**讲解点**：两条路线是刻意设计 —— 有两条，`choice` 才有真实的选择可做；
而且生成层不可用时，确定性路线就是降级方案。
另外"扩充工具链 = 改注册表，不需要重训模型"是这套设计的可维护性前提。

## 五个可现场演示的"亮点"

> 前三个是原有的；后两个（并发排队、文档与实现对齐）随 W1/W2/W3 一起来。

### 亮点一：确定性路线零成本降级

把 `.env` 里的 `LLM_API_KEY` 清空，重启服务，再跑一次「模板」类目标。
**链路照样成功** —— 生成式工具不可用，但确定性工具仍能完成任务。
这是"两条路线"设计的实际价值。

### 亮点二：失败可知，不静默

提交一个注定失败的目标（例如把 provider 指到不可用的端点），
观察：失败被分类（工具错误 / 计划错误 / 决策层不可用）、
按确定性状态机重试、换方案、最终熔断转人工，
**每一步都在界面上留痕**，而不是只给一个"失败了"。

### 亮点三：双 provider 产物逐字节一致

```powershell
$env:SANDBOX_PROVIDER='docker'   # 重启服务
# 跑同一个目标，对比 Local 与 Docker 下的产物
Get-FileHash artifacts\index.html -Algorithm SHA256
```

同一个目标在路径级隔离与容器级隔离下产出的文件 **SHA-256 逐字节相同** ——
这是沙盒抽象成立与否的最终验收，也是自动化测试里的一项。

### 亮点四：并发有上限，多了排队而不是压垮

`MAX_CONCURRENT_RUNS`（默认 2）决定"同时最多跑几个"。连点几次「开始创作」，
超出的运行进入**排队**并在列表里显示"队列第 N 位"，前面的跑完会**自动放行**；
队列满（`RUN_QUEUE_LIMIT`，默认 16）时 `POST /api/runs` 回 **429** 并说明上限。

**讲解点**：每个运行都会起一个沙盒（Docker 下是一个容器），所以这个数字直接
决定峰值 CPU / 内存 / 容器数。而**队列只在内存里**：服务重启后排队中的运行
不会被"复活"，而是被如实标成"已取消（服务重启）"——宁让人重新提交，
也不做一个没人盯着、状态还写着排队中的幽灵运行。

### 亮点五：文档与实现不符按缺陷处理

现场翻一处文档里的能力陈述，再在代码或测试里找到它的落点。
这条约定本身（见 `docs/用户要求与协作经验.md` §7.8）就是从一次真实偏差里长出来的：
文档写着"没有 Docker 时截图退化成占位图"，而实际行为是整次运行失败。
